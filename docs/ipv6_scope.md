# IPv6 Support Scope — TataElexy Adaptive QoS Engine

> **Document type:** Implementation scope & test coverage declaration  
> **Audience:** Evaluators, integration engineers, project stakeholders  
> **Last updated:** 2026-10-18  
> **Status:** Partial — code-complete, lab-untested on real IPv6 traffic

---

## 1. Executive Summary

TataElexy's QoS pipeline contains **code-level IPv6 support** throughout its filter
generation, filter parsing, and flow classification layers.  However, the lab testbed
(Linux network namespaces) was built exclusively on IPv4 addressing (`10.10.x.x/24`),
so **no IPv6 data-path exercise has been performed on real traffic**.  This document
records exactly what is implemented, what is not yet validated, and what would be
required for full IPv6 compliance.

> [!IMPORTANT]
> "Where available" (PS3 partial-credit clause) applies here.  The IPv6 code paths
> are present and reviewable, but runtime validation against live IPv6 flows is absent.

## 3. Code-Level IPv6 Implementation Details

### 3.1 Filter Command Generation — `linux_tc.py`

`render_filter_commands()` branches on IP version.  For each flow mapping provided,
it emits **both** an IPv4 `u32` filter command and an IPv6 `u32` filter command when
the mapping includes an IPv6 source address.

#### IPv4 filter (reference baseline)

```bash
# Generated by render_filter_commands() for ip version 4
tc filter add dev <IFACE> parent 1:0 protocol ip prio <PRIO> \
    u32 match ip src <SRC_IPV4>/32 \
    flowid 1:<CLASS>
```

Example with a real address:

```bash
tc filter add dev eth0 parent 1:0 protocol ip prio 10 \
    u32 match ip src 10.10.1.10/32 \
    flowid 1:10
```

#### IPv6 filter (128-bit source address matching)

```bash
# Generated by render_filter_commands() for ip version 6
tc filter add dev <IFACE> parent 1:0 protocol ipv6 prio <PRIO> \
    u32 match ip6 src <SRC_IPV6>/128 \
    flowid 1:<CLASS>
```

Example with a real address:

```bash
tc filter add dev eth0 parent 1:0 protocol ipv6 prio 10 \
    u32 match ip6 src fd00:4::10/128 \
    flowid 1:10
```

> [!NOTE]
> The `/128` prefix enforces **exact host-address matching**, equivalent to `/32` in
> IPv4.  The `u32` classifier decomposes the 128-bit IPv6 address into four 32-bit
> chunks internally; this is standard iproute2 behaviour and requires no special
> kernel patches on Linux ≥ 3.3.

### 3.2 `parse_filter_show()` — IPv6 Awareness

The filter parser (`parse_filter_show`) is written to recognise both `ip src` and
`ip6 src` tokens in `tc filter show` output.  Parsed IPv6 addresses are stored in the
same internal data structure as IPv4 addresses, keyed by IP version, allowing the rest
of the engine to consume them transparently.

### 3.3 Flow Classifier

The classifier's `protocol` field is **IP-version-agnostic**.  A flow record carries
the raw IP version as metadata; the classifier does not hard-code IPv4 assumptions.
An IPv6 flow arriving with the correct 5-tuple will be classified and mapped to a QoS
class by the same code path as an IPv4 flow.

### 3.4 Windows pktmon Capture

The Windows hotspot capture layer uses `pktmon`, which captures packet metadata for
**both IPv4 and IPv6 packets**.  IPv6 source/destination addresses and flow labels are
present in captured records and are forwarded to the classifier without filtering.

## 4. What Is NOT Implemented / Tested

1. **Lab testbed namespace addressing** — all client namespaces are on `10.10.x.x/24`
   (RFC 1918 IPv4).  No ULA (`fd00::/8`) or global unicast (`2001:db8::/32`) addresses
   are assigned to any namespace.
2. **Router IPv6 configuration** — the virtual router namespace has no IPv6 forwarding
   rules, no RA daemon (radvd / dnsmasq), and no NDP proxy configured.
3. **End-to-end IPv6 traffic generation** — no `iperf3 -6` or equivalent IPv6 traffic
   has been sent through the testbed.
4. **`tc` IPv6 filter runtime verification** — `tc filter show` output has never been
   captured for IPv6 filter entries during a live test run.
5. **Dual-stack simultaneous operation** — concurrent IPv4 + IPv6 classification under
   load has not been benchmarked.

## 5. What Would Be Required for Full IPv6 Validation

To move IPv6 from *code-complete* to *fully validated*, the following steps are needed:

### 5.1 Router Namespace

```bash
# Enable IPv6 forwarding
sysctl -w net.ipv6.conf.all.forwarding=1

# Assign a ULA prefix to the router's internal interface
ip -6 addr add fd00:4::1/64 dev veth-router-int

# (Optional) Advertise prefix via radvd or dnsmasq --enable-ra
```

### 5.2 Client Namespaces

```bash
# Example: assign IPv6 address to client namespace ns1
ip netns exec ns1 ip -6 addr add fd00:4::10/64 dev veth-ns1
ip netns exec ns1 ip -6 route add default via fd00:4::1
```

### 5.3 Traffic Generation

```bash
# iperf3 IPv6 server (in server namespace)
ip netns exec ns-server iperf3 -s -6

# iperf3 IPv6 client (in client namespace ns1)
ip netns exec ns1 iperf3 -c fd00:4::1 -6 -b 5M -t 30
```

### 5.4 Filter Verification

```bash
# Confirm IPv6 u32 filter is installed
tc filter show dev eth0 parent 1:0 protocol ipv6

# Expected output should contain lines similar to:
#   filter protocol ipv6 pref 10 u32 chain 0
#   match ip6 src fd00:4::10/128 at 8
```

### 5.5 Regression Checks

- Run `pytest tests/` with an IPv6-addressed mock flow record and assert the correct
  `flowid` is returned.
- Capture and diff `tc filter show` before and after `apply_qos()` for an IPv6 mapping.

## 6. IPv6 Compliance Checklist

Use this checklist when reporting compliance status to evaluators:

- [x] `linux_tc.py` generates `u32 match ip6 src <addr>/128` commands
- [x] `render_filter_commands()` handles IP version 4 **and** 6 in a single function
- [x] `parse_filter_show()` recognises and parses IPv6 filter entries from `tc` output
- [x] Flow classifier accepts IPv6 5-tuples without code changes
- [x] Windows pktmon capture layer preserves IPv6 address fields
- [x] `tc` command syntax uses correct `protocol ipv6` flag (not `protocol ip`)
- [x] 128-bit host matching (`/128`) is used — no accidental subnet over-matching
- [ ] Lab testbed client namespaces have IPv6 addresses assigned
- [ ] Router namespace has IPv6 forwarding and prefix delegation configured
- [ ] End-to-end IPv6 iperf3 test executed and QoS classes observed
- [ ] `tc filter show` output verified for live IPv6 filter entries
- [ ] Dual-stack (IPv4 + IPv6 simultaneous) load test completed
- [ ] Unit tests updated with IPv6 flow records and assertions

## 7. PS3 Constraint — Partial Credit Declaration

> **Constraint language:** *"IPv6 support — where available"*

**Claim:** IPv6 support is **available at the code level** in `linux_tc.py`,
`parse_filter_show`, and the flow classifier.  The exact `tc` commands that would be
issued for IPv6 are documented in §3.1 above and are syntactically correct per
iproute2 documentation.

**Limitation:** Real-traffic validation has not been performed due to the IPv4-only
lab testbed.  This limitation is **documented explicitly** in §4, and the remediation
path is detailed in §5.

**Partial credit basis:** The implementation demonstrates architectural readiness for
IPv6.  No code changes are needed to generate correct IPv6 `tc` filter commands — only
the testbed environment configuration (namespace addressing + router setup) is missing.
